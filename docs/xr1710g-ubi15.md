# XR1710G legacy UBI 1.5 experimental build

Use `1710-ubi15.config` on the repair branch. This is a separate target;
`1710.config` and both existing XR1710G layouts retain their meanings.

The new target is based on a device report showing:

| Partition | Offset | Size |
| --- | --- | --- |
| vendor | 0x00000000 | 0x00600000 |
| chainloader | 0x00600000 | 0x00100000 |
| ubi | 0x00700000 | 0x1d9c0000 |
| reserved_bmt | 0x1e0c0000 | 0x01f40000 |

The reported UBI contains static `fit`, redundant `ubootenv`/`ubootenv2`,
static `factory` (24582 data bytes), and `rootfs_data`. The factory format
is the legacy repacked EEPROM at 0, binary WAN MAC at 0x5000, and binary
LAN MAC at 0x6000. It is **not** the complete stock DSD format used by the
new bl2/fip layout. Offsets must still be checked against the particular
device's backup before any boot test. Never publish device backups.

The image includes DS-Lite and its matching IPv6 tunnel module. Build
checks require the NPU enabled in the final kernel config and retain the
wireless/PON isolation checks. Neither compilation nor these checks prove
runtime NPU operation, DS-Lite offload, network connectivity, or boot safety.

## Deliberate upgrade restrictions

The image advertises only `gemtek,xr1710g-ubi15`, with compatibility 1.5.
It does not advertise the ambiguous existing `gemtek,xr1710g-ubi` ID.
Normal upgrades from that ID must fail instead of silently accepting a
different layout. This experimental target also refuses future sysupgrade
operations in both platform check and write paths pending validation.
It has no bootloader image and no automatic boot-environment setup or
compatibility migration. Vendor, chainloader and reserved partitions are
read-only. Experimental builds are excluded from automatic Releases.

Do not force an upgrade or write NAND/UBI volumes to bypass these guards.
Before enabling an upgrade path, verify the compiled FIT device tree and
metadata, exact running MTD offsets/sizes, factory format, bootloader
memory/boot requirements, and an independently usable recovery method.

## Kernel diagnostics

Every build exports the final kernel config, input/override fragments,
Airoha Kconfig, built-in module list, and XR1710G device trees under
`diagnostics/`. The config is selected only from the immediate
`linux-[0-9]*/.config` source directory. Missing or ambiguous candidates fail;
nested tool/backports configs cannot satisfy the check.

The previous recursive `*/linux-*/.config` pattern also matched any nested
config below `linux-airoha_an7581`. That makes a wrong-file selection
possible, but the previous artifact did not retain its selected config,
so the cause of its NPU validation failure is not yet proven.
